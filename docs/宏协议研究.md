# 官方宏协议分析与存储实测

分析对象为用户提供的 CHERRY Utility 2.3.28.7 Windows 安装程序中主程序。下面区分本地静态分析与 USB 实物测试，不是官方公布的协议。仓库不分发官方程序或反汇编全文。

## 宏写入路径

主程序中宏配置序列化调用 `0x4DBD90`，普通固件生成 Report 4 / 命令 `15`；另一固件分支使用 `95`。生成分块长度、两字节偏移、标志 00、内容，并计算请求校验后调用 HID 输出路径。

调用者 `0x500269` 的基址为 `设备容量字节 × 128 × 配置索引`。该设备容量字节位于设备信息结构的第 6 字节；目标键盘读取值为 24，对应 3072 字节容量。配置索引含义尚未确认，当前只研究偏移 0 的宏区，不尝试其他配置区。

## 数据结构

序列化函数先收集绑定到物理键的宏动作，`ActionType = 2` 进入宏路径。

| 区域 | 静态分析观察 |
| --- | --- |
| 0–1 | 小端 55AA，即字节 AA 55 |
| 2–3 | 本次序列化数据总长度，小端 |
| 4–5 | 收集到的宏数量，小端 |
| 前 16 字节其余部分 | 官方程序使用未清零堆内存；当前编码置零，短宏存储实测接受；执行效果待验证 |
| 16 起 | 每个宏的两字节偏移表 |
| 每宏数据头 | 事件数量小端两字节，指针再推进 4 字节；剩余两字节同样来自未清零内存，当前编码置零 |
| 每事件 | 4 字节，来源为 ActionMacroEvents |

事件转换函数 `0x480B80` 从官方 JSON 的 `Delay`、`Type`、`Button`、`Action` 生成如下四字节记录：

| 字节 | 含义 |
| --- | --- |
| 0、1 | Delay 的小端整数 |
| 2 | Type；Action 等于 down 时设置最高位 80 |
| 3 | Button 的低字节 |

普通键 `Type = 10`，Button 为 HID Usage；修饰键 `Type = 9`，Button 为单个位掩码，依次对应左 Ctrl、Shift、Alt、Win、右 Ctrl、Shift、Alt、Win，不能直接写 E0…E7。鼠标按钮为类型 1；进一步分析确认类型 4/5 是 X/Y 移动，不能当作滚轮使用，早期此处的滚动解释已纠正。移动与滚轮的本型号支持范围仍在核对，见[扩展动作核对](文本与鼠标扩展动作核对.md)。延迟发生在事件前还是事件后，仍需实体执行确认。

单次宏绑定为键位三字节记录 `[70, 宏索引, 00]`。其他宏类型使用 70 的模式值或 71 的循环计数。0.10.0／Web 0.4.0 已支持这些模式的读取、导入、编辑与导出；全部宏实体写入仍暂停，中止方式尚需实物验证。具体分支见[执行模式移植](宏执行模式移植.md)。

宏总长度为 `16 + 6 × 宏数量 + 4 × 全部事件数量`。应用检查容量、偏移、事件数量和按下/松开平衡；未知类型或损坏数据只保留原始备份，不猜测解析。

### 读取后编辑的保留字节

当前源码在读取后编辑时保留总头部 6…15 字节，以及每宏数据头的第 2…3 字节；后者存于可选 `hardwareReserved` 字段，必须恰为两个字节。修改、改名与复制保留该字段，宏记录移动后按其新偏移写回；未携带此字段的新宏沿用零值。全部宏清空仍生成空库，头部和每宏保留字节不解释为执行参数。旧配置无需添加新字段即可读取。

原生／网页针对性检查用非零保留字节确认读取再解析编码、步骤修改、复制、删除和配置保存后的保留行为；没有连接硬件。前述静态分析观察不等于已确认这些字节的固件语义，也不据此承诺保留所有未知扩展布局。此前 0.14.1／Web 0.8.0 包未包含此次源码修正；统一验收前需更新包。

## USB 存储实测

命令 14 按偏移读取宏区，54 字节分块成功，56 字节被拒绝。偏移 0…3070 共 3071 字节可读，偏移 3071 被拒绝；因此应用不读取或写入最后一个容量字节。

原宏区全部为零，且没有宏绑定。测试写入一个 30 字节短宏：A 按下、A 松开，延迟分别为 0 和 50；未把它绑定到任何实体键。15 回显通过后，14 完整读回的 3071 字节与预期一致，键位、灯效参数与颜色未改变。随后恢复原来的 30 个零字节，再次完整读取确认原宏区及其他配置均已恢复。

此测试证明该键盘接受宏存储读写，不能证明实体键执行、保留字节语义、延迟语义或断电保存。

## 当前实现与下一步

应用已有宏编辑、按下/松开平衡检查、配置导入导出、从宏区解码和实验性的联合写入按钮。

联合写入先保存包含原宏区的备份，在每个写入和恢复分块前检查松键。若原宏绑定存在且宏区改变，先禁用原绑定并等待原单次宏的最长有限延迟结束；写事件块，最后写头部和指针块，完整读取宏区，再写键位表，最后校验键位、宏区与灯效。失败时解除新旧宏绑定、等待有限宏结束，再恢复原宏区与键位。无法确认松键时停止写入并报告备份路径。

联合写入和失败恢复已做模拟固件测试。随后在本机 USB 上使用同一生产方法，写入一个 A、B 单次宏并绑定计算器键，完整读回一致。测试窗口两分钟内未收到实体按键，超时后解除绑定、等待宏的有限时长、恢复原宏区与键位，并完整校验原灯效、键位和宏区均已恢复；系统修饰键状态为 0。

这确认了绑定宏的联合写入与正常恢复流程，不能证明实体触发与延迟语义；也没有覆盖真实通信失败。实体触发、延迟语义及断电保存仍待验证。95 分支未发送。

## 2026-10-06：容量检查与软件限制的来源区分

完整追踪本型号虚方法 +0x2B4（4FF710..50035A）。发送器先遍历物理映射和非零动作链接，收集 ActionType=2 的绑定；按收集数量加入两字节指针和四字节宏头，再按每个事件四字节累加，最后加 16 字节总头。在 4FFC2F 将总长度与 byte(device+0x1DFA) 左移七位比较，允许等于名义容量。本型号已知容量字节 24 对应名义 3072 字节，但实读可访问区仍为 3071 字节，两者不能混同；当前不会使用最后一个不可访问字节。

总库宏数量、每宏事件数量与事件循环计数使用 16 位字段。4FFF9B 将 JSON 事件数组大小写入 word；4FFFB5／4FFFCF 分别写低、高字节；50000F 用该数量结束事件循环，并由 480B80 编成四字节事件。此完整发送方法未显示 32 个宏或 256 个事件的固定限制。CherryMac 当前存在这两个校验限制，它们是本软件当前范围，尚未证明为官方编辑器或固件上限；仍需追踪官方编辑器检查，不能只因 word 编码就承诺固件接受大宏。此次没有直接放宽产品限制或写入授权。

若没有收集到已绑定宏，4FFA2F 的零分支经 4FFAE3 提前返回 0，不进入分配、构造和 500269 的宏库发送。因此这段方法中的“没有宏绑定”不是空宏库擦除命令。开始阶段仍会读取设备资料，其他调用和固件隐含影响不在该提前返回结论中；完整默认宏存储语义继续 pending。

只读工具 v39 加入 31 处指令、目标虚表入口及完整发送器哈希，核对名义容量公式、数量位宽、空绑定返回和宏区发送基址。对固定版本官方 EXE 与型号资源核对通过，私有结果为 work/official-macro-capacity-audit-20261006.json。没有运行程序、行为测试或访问键盘；App、PHP 与线上运行文件未变。下一步继续检查宏编辑器的数量检查以及收集／索引关系，再决定如何补齐当前范围。

## 2026-10-06：编辑器容量上限与重复绑定

本型号虚表 +0x260 指向 4F7D20。它在 4F8399…4F83BC 读取同一容量字节，将 `(容量字节 × 128 − 22) / 4` 向零取整后，经 45E370 写入宏控件 +0x9DC。已知容量字节 24 对应 **762 个事件**。这里的 22 字节是一个宏的 16 字节总头、2 字节指针和 4 字节事件头；不是把整个宏库按每个宏都允许 762 事件处理。库内多个绑定仍受总字节容量检查。录制的一条已追踪路径在 453C78 对比该成员与 `macro_action_list` 的数量，达到上限后发消息 0C1B；4940CA 转交 4B4F90，零参数分支显示 `message_text_27`（“宏动作数量已达上限”）。该结果证明当前软件的 256 事件范围不等于这一官方编辑器上限，不能直接证明固件执行 762 事件。

宏发送器每遇到一个可映射、非零 ActionLink、ActionType=2 的绑定，就将 ActionLinkIndex 追加到数组并增加数量。482B50 的前置 422750 比较的是来源指针与数组首尾地址，用于处理输入别名；没有按动作索引值去重。序列化循环在 4FFF08 逐项取数组值，4FFF23 查回 ActionInfo。因此两个按键引用同一个官方宏，仍产生两条存储记录，容量按事件数量重复计算；未绑定的宏库条目不进入这个收集过程。

相应的键位发送器先将宏序号清零（4FF00F），在 70／71 记录的第二字节放入当前序号，经过宏分支后增加一（4FF333）。动作库索引与固件宏序号是不同编号，移植不能直接复用 ActionLinkIndex。

CherryMac 当前采用按宏库顺序编码、多个键共享记录的布局，并限制 32 个宏／256 个事件。上述官方布局差异不表示当前共享布局已经被证明无效，也不允许无提示重排已有键位的索引。后续补齐需同步重建键位引用和宏区、保持未绑定的用户草稿，并处理读回后重复记录的编辑身份；这些兼容工作仍未完成。原始备份及既有 3071 字节访问范围保留。

只读工具 v40 新增 49 处固定指令、本型号编辑器虚表入口、4 个完整函数摘要与 2 个资源字符串核对；实际官方文件核对通过。没有执行官方程序、行为测试或访问硬件，未修改产品写入路径。

## 两端官方绑定布局转换模型

新增原生 `OfficialMacroStorageLayout.prepare` 和网页 `prepareOfficialMacroStorage`，根据调用者提供的完整固件默认键位表，按实际逻辑匹配顺序生成独立宏记录和按键绑定序号，逐绑定计算容量。多个按键引用同一草稿时分别编码；未绑定的宏仍留在调用者的草稿库，不计入存储。模型支持按已确认编辑器公式检查事件数量，同时维持已实读的 3071 字节范围，保留总头十字节及每条记录两字节不透明数据。空绑定返回 bank=nil／null，表示不发送宏区，而非零填充擦除。每条结果带 logicalIndex、physicalSlot、libraryIndex 与 ordinal，避免混用编号。

这两个纯数据模型返回 hardwareReady=false，没有接入产品发送器，也不访问键盘。生产共享宏写入、32／256 范围与现有配置格式保持；新的按绑定布局尚需衔接读回编辑身份、恢复事务、导入导出和界面容量显示。默认表出现会影响绑定的逻辑别名时拒绝转换，不能自行假定别名对应关系。没有进行行为／模拟或真机测试，只核对源码和语法／类型、编译打包。
