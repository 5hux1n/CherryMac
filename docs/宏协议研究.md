# 官方宏协议分析与存储实测

分析对象为用户提供的 CHERRY Utility 2.3.28.7 Windows 安装程序中主程序。下面区分本地静态分析与 USB 实物测试，不是官方公布的协议。仓库不分发官方程序或反汇编全文。

## 宏写入路径

主程序中宏配置序列化调用 `0x4DBD90`，普通固件生成 Report 4 / 命令 `15`；另一固件分支使用 `95`。生成分块长度、两字节偏移、标志 00、内容，并计算请求校验后调用 HID 输出路径。

调用者 `0x500269` 的基址为 `设备容量字节 × 128 × 配置索引`。该设备容量字节位于设备信息结构的第 6 字节；目标键盘读取值为 24，对应 3072 字节容量。配置索引含义尚未确认，当前只研究偏移 0 的宏区，不尝试其他配置区。

## 数据结构

序列化函数先收集绑定到物理键的宏动作，`ActionType = 2` 进入宏路径。

| 区域 | 静态分析观察 |
| --- | --- |
| 0–1 | 小端 55AA，即字节 AA 55 |
| 2–3 | 本次序列化数据总长度，小端 |
| 4–5 | 收集到的宏数量，小端 |
| 前 16 字节其余部分 | 官方程序使用未清零堆内存；当前编码置零，短宏存储实测接受；执行效果待验证 |
| 16 起 | 每个宏的两字节偏移表 |
| 每宏数据头 | 事件数量小端两字节，指针再推进 4 字节；剩余两字节同样来自未清零内存，当前编码置零 |
| 每事件 | 4 字节，来源为 ActionMacroEvents |

事件转换函数 `0x480B80` 从官方 JSON 的 `Delay`、`Type`、`Button`、`Action` 生成如下四字节记录：

| 字节 | 含义 |
| --- | --- |
| 0、1 | Delay 的小端整数 |
| 2 | Type；Action 等于 down 时设置最高位 80 |
| 3 | Button 的低字节 |

普通键 `Type = 10`，Button 为 HID Usage；修饰键 `Type = 9`，Button 为单个位掩码，依次对应左 Ctrl、Shift、Alt、Win、右 Ctrl、Shift、Alt、Win，不能直接写 E0…E7。鼠标为类型 1，滚动为类型 4/5，当前未实现。延迟发生在事件前还是事件后，仍需实体执行确认。

单次宏绑定为键位三字节记录 `[70, 宏索引, 00]`。其他宏类型使用 70 的模式值或 71 的循环计数。0.10.0／Web 0.4.0 已支持这些模式的读取、导入、编辑与导出；全部宏实体写入仍暂停，中止方式尚需实物验证。具体分支见[执行模式移植](宏执行模式移植.md)。

宏总长度为 `16 + 6 × 宏数量 + 4 × 全部事件数量`。应用检查容量、偏移、事件数量和按下/松开平衡；未知类型或损坏数据只保留原始备份，不猜测解析。

## USB 存储实测

命令 14 按偏移读取宏区，54 字节分块成功，56 字节被拒绝。偏移 0…3070 共 3071 字节可读，偏移 3071 被拒绝；因此应用不读取或写入最后一个容量字节。

原宏区全部为零，且没有宏绑定。测试写入一个 30 字节短宏：A 按下、A 松开，延迟分别为 0 和 50；未把它绑定到任何实体键。15 回显通过后，14 完整读回的 3071 字节与预期一致，键位、灯效参数与颜色未改变。随后恢复原来的 30 个零字节，再次完整读取确认原宏区及其他配置均已恢复。

此测试证明该键盘接受宏存储读写，不能证明实体键执行、保留字节语义、延迟语义或断电保存。

## 当前实现与下一步

应用已有宏编辑、按下/松开平衡检查、配置导入导出、从宏区解码和实验性的联合写入按钮。

联合写入先保存包含原宏区的备份，在每个写入和恢复分块前检查松键。若原宏绑定存在且宏区改变，先禁用原绑定并等待原单次宏的最长有限延迟结束；写事件块，最后写头部和指针块，完整读取宏区，再写键位表，最后校验键位、宏区与灯效。失败时解除新旧宏绑定、等待有限宏结束，再恢复原宏区与键位。无法确认松键时停止写入并报告备份路径。

联合写入和失败恢复已做模拟固件测试。随后在本机 USB 上使用同一生产方法，写入一个 A、B 单次宏并绑定计算器键，完整读回一致。测试窗口两分钟内未收到实体按键，超时后解除绑定、等待宏的有限时长、恢复原宏区与键位，并完整校验原灯效、键位和宏区均已恢复；系统修饰键状态为 0。

这确认了绑定宏的联合写入与正常恢复流程，不能证明实体触发与延迟语义；也没有覆盖真实通信失败。实体触发、延迟语义及断电保存仍待验证。95 分支未发送。
