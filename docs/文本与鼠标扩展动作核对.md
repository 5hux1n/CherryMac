# 文本与鼠标扩展动作的官方路径

本页基于用户提供的 CHERRY Utility 2.3.28.7 主程序与 CommFunc.dll 静态分析。没有执行 Windows 程序，没有向键盘发送测试包；这些证据不能替代本型号真机验收。

## 文本动作

主程序动作分派表 `0x4FF6F4` 将 ActionType 2 分派到宏事件路径，将 ActionType 3 分派到 `0x4FF341` 的文本路径。这是两个不同的动作类型。

文本分支读取 `ActionContent.ActionText`，调用字符串转换函数 `0x480FB0`，保存到设备对象的 `+0x2590` 文本表。该分支没有把文本转换为宏区的四字节事件；2026-10-03 核对 IAT `0x6EB87C` 后确认它是 DuiLib 的 `CDuiString::IsEmpty`：返回非零时跳过设置，返回零（非空）才写入 `A1 00 00`。此前“空字符串写入”的记录反了，现纠正。空文本保持零临时记录，由后续流程跳过更新，不能把它解释成禁用。

另一个文本调用路径在 `0x512EBA` 读取同一文本表，在 `0x512EF1` 传入操作值 `0x291`，通过对象的 `+0xA34` 函数指针调用。初始化路径 `0x4F68D3–0x4F68EB` 通过 GetProcAddress 取得 CommFunc.dll 的 `UniFunc2` 导出并保存该指针。

DLL 的 `UniFunc2` 在 `0x10001FF3–0x10002004` 识别 `0x291`，调用 `0x10001EC0` 创建线程。线程入口 `0x10001E30` 使用 GetForegroundWindow、GetWindowThreadProcessId、AttachThreadInput 与 GetFocus 获取主机上的焦点窗口，循环通过 SendMessageW 发送文本的 UTF-16 代码单元，消息数值为 `0x286`；循环跳过 `0x000A`。

这确认了官方存在依赖 Windows 主机的文本执行路径。仍需确认该型号的实体触发、ActionTextFlag 和非空文本键位编码，再决定完整移植方式。不能把任意 Unicode 文本当作已确认的键盘板载宏，也不能只凭这条路径排除其他型号或分支的实现。

完整移植目标保留文本功能。macOS 需实现对应主机端能力；浏览器页面的跨应用文本执行方式需要另行落实。当前两端仍原子拒绝未支持的文本绑定导入，避免静默丢失或生成错误硬件映射。

## Type 4／5 的纠正

早期宏协议文档将 Type 4／5 写为滚动，现已纠正。公共事件构造函数 `0x45C840` 对消息 `0x200` 的扩展路径，在 `0x45CB10` 选择事件字节 `0x84` 并读取 `kb_mouse_x_left_edit`，在 `0x45CBC5` 选择 `0x04` 并读取 `kb_mouse_x_right_edit`；后续分支对应 Y 轴控件。去掉事件字节最高位后，类型为 4／5。这是 X／Y 移动路径，不能当作滚轮方向或滚轮次数使用。

公共表还包含鼠标滚轮消息 `0x020A`，但已追踪的宏录制函数只匹配基本与扩展按钮消息，手工宏菜单只列出左、中、右、前进、后退五按钮。仅凭公共表不足以证明本型号能录制或执行滚轮，也不能排除尚未追踪的型号分支。暂不猜测滚轮编码，原始备份继续保留未知事件。

构造函数 `0x45C840` 的十个直接调用点位于 `0x45D8D0–0x45DAA2`，传入的是五个鼠标按钮的按下／松开消息；未见这些调用传入 `0x200`。软件资源的宏动作菜单也只有五个按钮及编辑／插入事件，尚不能据公共构造函数中存在轴移动分支就宣称型号 47 提供轴移动宏。继续追踪间接调用和型号 UI 分支；不据此删减完整功能目标。

## 文本触发的静态接收分派

继续追踪得到 `CEevisionKeyboardDevice` 表 `0x77F604` 的虚函数 `+0x32C` 指向文本执行函数 `0x512DE0`。不能仅搜索直接 `call 0x512DE0`；接收代码先加载函数指针再间接调用。通用接收路径 `0x50C227–0x50C266` 判断事件值在 `[0x0700, 0x0800)`，减去 `0x0700` 后把索引传给此虚函数。另一条接收路径 `0x50C69A–0x50C6C6` 做同样的区间与索引分派。后一条路径在 `0x50C4A8–0x50C4CA` 用接收缓冲区的字节 1 和 2 构造小端 16 位事件值；这只是该通用分支的布局，不能直接套到目标型号全部报告。

文本执行函数继续通过逻辑键值表 `+0x2130` 搜索索引，再从 `+0x2590` 文本表取非空内容，传给 `UniFunc2(0x291, ...)`。这进一步说明官方文本由专用事件触发后交给主机执行，不是普通键盘字母报告，也不是将整个文本写成宏事件。文本键位编码仍与触发事件值不同，不能把 `A1 00 00` 当作接收报告格式。

只读工具 `Tools/inspect-official-settings.py` 已增加虚函数目标核对及两个接收分支的八处指令核对；固定版本 SHA-256 后读取 PE 文件，不执行 EXE。原文件核对及四项 PE 工具检查通过。报告明确不证明型号 47 类选择、实际报告 ID／布局、文本实体执行或持久化。还需追踪 `046A:01CE` 的接口选择与报告描述符／接收入口，才能落实原生文本监听和网页端的主机能力范围；当前不生成真实文本绑定写包。

## 本型号资源、工厂与接收线程进一步关联

只读工具现在可额外传入 `--skin` 指向解包的资源目录。固定 EXE 哈希后，核对初始化指令：`0x406C4A–0x406C5E` 将型号 47、VID 046A、PID 01CE 注册到同一条目；`0x406C82` 引用宝可梦型号的 DeviceOption 资源路径。目标设备 XML 第一层选择 `EevisionKeyboardDevice`，工厂 `0x488E7D` 比较该类名，匹配分支 `0x488EBA` 调用 `0x4F6060`，构造器 `0x4F609A` 安装已核对的 `0x77F604` 虚函数表。这比仅在 EXE 中找到共用类和文本函数更强，但还不是实际运行时跟踪。

原始事件连接入口 `0x50B050` 在参数值 1 分支打开对象 `+0x17B4` 的接收连接，`0x50B165` 调用启动函数 `0x50B5C0`；启动函数把 `0x50C3D0` 作为线程入口。线程读回同一连接的缓冲区，复制九字节，再从字节 1／2 得到事件值，进入已确认的文本索引分派。另一个 `0x50B480` 启动的 `0x50BEE0` 路径使用 HID 解析函数，并非同一原始九字节读取方式；两条路径不能混用。

工具增加十二处固定版本指令检查，并记录本型号两份 XML 的哈希。真实资源及 EXE 检查通过；合成资源检查验证错误类名和错误型号名称会被拒绝。资源不复制到公开仓库。

九字节复制仍不足以证明 Report ID 为 5：接口支持多份输入报告，读取代码未在此处检查 ID。实际文本触发的报告 ID、索引与物理键对应、ActionTextFlag 的用途仍需确认；当前没有生成文本写包或监听实体键。下一步继续追踪该连接的接口筛选及文本键位设置路径，避免重复分析已确定的主机执行函数。

```sh
python3 Tools/inspect-official-settings.py /绝对路径/CHERRY-Utility-Software.exe --skin /绝对路径/Skin
```

## 文本标志、键位记录与主机执行核心

继续核对同一官方版本：文本设置 `0x4FF3F7` 在字符串非空时落入 `0x4FF3F9–0x4FF407`，生成 `A1 00 00`，后续非零记录才写入三字节键位表。空文本跳过更新，不能等同于禁用。`ActionTextFlag` 的唯一已定位字符串引用在 `0x512064`；前面的 `0x512047` 为 JSON 数值构造传入常数 1。该字段位于动作对象顶层，与 ActionContent 同级；ActionText 位于 ActionContent 内。该导出路径固定写 1，不能把它猜成执行模式或固件存储标志，也不能据字符串引用排除其他间接路径。

两端新增纯 `HostTextPlan` 解析，保留原文本和原标志；另计算官方兼容的执行数据：NUL 前缀、跳过 LF、保留 CR，空原字符串不产生更新记录，只有 LF 的非空字符串仍有 A1 记录但无执行字符。事件值 0700…07FF 减去 0700；结果仍需通过官方逻辑键值表对应文本，不能直接当 USB 矩阵槽位。

Mac 增加主机执行核心，使用 Unicode 键盘事件并将 surrogate pair 保持在同一事件对内，按下后始终发送松开。只接受已知标志 1 或缺失标志；需要辅助功能权限及明确目标应用，焦点变化、修饰键按住、目标退出或取消会中止。异步执行在事件对之间让出主线程，不改剪贴板，不安装监听，也不生成键盘配置包。调用返回的计数是已发送的 UTF-16 单元，不证明目标应用已采用文本；部分应用可能忽略 Unicode 事件，仍需实际应用验收。

**执行核心尚未连接实体触发或产品界面。** 文本绑定导入仍拒绝写入，提示主机服务和触发格式尚待落实，原编辑区保留。网页只有同样的文本解析计划，尚无跨应用执行通道，不能用页面内填字或复制替代完整功能。此前 Mac 0.15.0／Web 0.9.0 包未包含这次核心增量。

本轮只做针对性编译及纯文本计划检查，覆盖中文、emoji、CR/LF、NUL、空文本、事件边界和网页导入失败时原配置保留；没有调用执行器、查询或申请权限、安装监听、发送文本或访问 HID。固定版本指令核对通过。

## 文本事件到逻辑键的对应实现

定位到 `0x5031F0` 的对应表构造：遍历 126 个逻辑项，逐个匹配固件默认键位表的三字节记录；匹配后保存物理槽位，第一处匹配即退出。文本事件分派减去 0700 后，使用这个槽位回查逻辑键，再取对应文本。`0x4FC2F4` 在初始化读取之后调用该构造器；`0x4DC340` 确认默认键位读取命令为 07。它与当前设置读取命令 08 是不同数据来源，不能用已修改的当前键位表代替默认表。

046A:01CE 的非零 PID 分支、排除另一个 01BA 型号后，匹配参考表为 `0x76C6C8`，由 126 组三个 DWORD 组成，每个值都在字节范围内且记录互不重复。该表与型号 47 JSON 的 DefaultAssignment 在 14 处国际键／Fn 等位置不同。两端新增独立的 `firmwareLogicalDefaults`／`FIRMWARE_LOGICAL_DEFAULTS`，保留既有 JSON 指纹不变；完整 126 条记录与固定版本 EXE 对照一致。

两端 `resolveHostTextTrigger` 要求调用方提供完整默认表，返回逻辑索引及物理槽位。未匹配、事件越界或默认表里的后续重复记录不产生文本分派，避免把 FF 未对应项或另一键的文本当成当前键。离线合成默认表覆盖计算器槽位 102 → 逻辑项 17、Fn 参考差异和重复记录；这些是解析检查，不证明实体文本报告或默认表实机读取已验证。

本轮未读取真实键盘、未发送写包或启动主机输入服务。报告 ID 仍未确定；下一步继续核对该接收连接的接口筛选，并接通已确认报告后的文本绑定路由。当前解析核心仍不进入普通键位写入授权范围。

## 官方配置动作到文本路由的接线

两端新增准备路由的 `HostTextBindings`／`prepareHostTextBindings`：先核对型号 47、126 个默认指纹、完整默认表和当前表，再把默认表匹配得到的逻辑项对应到 KeyList。当前物理记录须为 A1 00 00、ActionLink 须为 1、ActionLinkIndex 须有效且指向 ActionType 3，才建立文本路由。普通媒体记录、空文本、未知事件或后续重复默认记录不产生路由；无效动作引用使整次准备失败。

路由保留动作索引、逻辑索引、物理槽位及文本执行计划。准备后的配置独立于编辑草稿；网页返回计划副本，修改返回值不能污染下一次分派。中文／emoji 文本保留。定向离线检查覆盖槽位 102 → KeyList 17 → ActionInfo 0 → 对应文本、媒体记录拒绝、无效引用拒绝及草稿隔离；原生编译和纯文本检查通过，没有执行文本或访问 HID。

这仍是数据路由，**不是报告来源授权**。接收服务还须确认真实设备、报告格式和该次连接的读回数据，配置变化或重连后须重新准备，不能仅凭保存的 JSON 恢复监听。当前没有接入实体报告回调、文本键位写入或跨应用网页执行，也没有更新之前的预览包。

## 接口登记字段与报告 ID 分离

固定版本初始化 `0x4120B1`、`0x412147`、`0x4121E0` 为 046A:01CE 登记三行接口资料。只读核对工具现在解码这些直线常量赋值，得到以下值；不运行 Windows 指令，不允许跳转、调用或越界写入。Windows 路径集合编号不能直接用于 macOS 接口匹配。

| Windows 路径 MI | COL | Usage Page | Usage | 登记行 +8 | 登记行 +A |
| --- | --- | --- | --- | --- | --- |
| 0 | 4 | FF1C | 92 | 1 | 0 |
| 0 | 3 | 000C | 1 | 1 | FF |
| 0 | 5 | FF1C | 92 | 1 | FE |

路径解析函数 `0x485CD0` 查找 `&mi_`，`0x485D20` 查找 `&col`；枚举代码将它们写入行 +4／+6。`HidP_GetCaps` 的输出位于 HID 包装对象 +22C，枚举从其中取 UsagePage／Usage，写入行 +E／+10。结构语义依据 [Microsoft HIDP_CAPS 文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps)。

`0x4978BA–0x4978C1` 则把登记行 +8 的连接选择值复制到枚举行 +8；它不是 Usage、UsagePage 或 Report ID。`0x4A05DB` 比较的是这个值，`0x4A05EA` 传入连接参数 1，`0x4A064D` 调用原始接收连接。+A 的二级值通过设备元数据设置另行传递，尚未将它解释为确定的报告用途。

原始接收线程 `0x50C45E` 使用 HIDP_CAPS.InputReportByteLength，之后复制前九字节。Microsoft 文档说明该长度是集合所有输入报告的**最大**长度并包含报告 ID；九字节复制不是“实际报告必须九字节”的检查。两个厂商登记行的 Usage 也相同，不能只用 Usage 或复制长度宣布 Report 5 就是文本触发。已保存描述符中的 Report 4 配置回复与 Report 5 短报告仍须分别核对。

工具审计格式更新为 3，新增三行实际初始化值、字段偏移及十四处指令核对。固定 EXE／资源核对通过；必要工具检查共六项通过，新增解码拒绝未知指令、缺失寄存器值、重复／越界存储和不完整行。未连接 HID、调用文本执行器、安装监听、写入配置或更新预览包。下一步继续追踪 +A 的分派和两个厂商集合的接收用途，再接实体触发服务。

## 二级 FE 分派与 Report 5 的静态关联

继续追踪得到：`0x49878D` 取行 +8 为连接参数，`0x4987AC` 取行 +A；`0x4987CB–0x4987D5` 判断 FE 后进入 `0x498E3B`，`0x498E4C` 调用 `0x49FBA0`。该函数把连接参数减一，查表 `0x4A0A10`。本型号参数为 1，首项指向 `0x4A04C6`，再进入已确认的 `0x50B050` 原始接收路径。因此目标登记 COL 5／FE 与原始文本事件接收已形成静态关联，而不是凭报告长度推测。

纯文件描述符工具增加每个字段的 `topLevelCollectionOrdinal`，嵌套集合不增加顶层序号。现有目标 USB 描述符显示顶层 3 为媒体 Report 3，顶层 4 为厂商 Report 4（64 字节），顶层 5 为厂商 Report 5（9 字节）。该对应与官方 MI 0／COL 3、4、5 的 Usage 一致，**静态关联指向 Report 5**。尚未捕获实际文本配置后的实体事件，不能据此称文本功能已通过真机验收。

两端新增纯 `hostTextEvent`／`officialHostTextEvent` 解码：要求包含 ID 的完整九字节报告、ID 为 5、字节 1／2 组成的小端事件值在 0700…077D（126 个物理槽位）。其余尾部字段不猜测语义。Report 4、过短／过长数据及越界槽位不产生文本事件。WebHID 的 reportId 与 payload 分离，接收适配器须明确拼成完整报告；解码自身不安装监听、不授权设备，也不发送文本。

固定 EXE 核对工具追加七处 FE 分派指令及跳转表首项核对；实际文件通过。描述符集合序号的必要检查通过，两端解码拒绝配置回复／长度错误／越界的检查及原生编译通过。新核心尚未接入产品监听、真实默认表读取、文本绑定写入或网页跨应用主机服务；旧预览包未替换，没有 HID 操作或权限申请。下一步接收服务可按 Report 5 建立来源与会话校验，再关联已准备的文本路由。

## 显式报告观察与会话失效

两端新增 `startHostTextObservation`／`stopHostTextObservation` 入口，启动时重新准备默认／当前表路由，默认没有开启。客户端沿用已经绑定到唯一目标 USB 设备的输入回调，只将有效 Report 5 交给文本路由；保持 Report 4 的配置回复队列及既有研究观察回调。回调带不可变会话 UUID，后续执行器须在使用时核对当前 `hostTextObservationToken`。停止、更换观察、配置变更请求、传输错误和设备断开都会清除路由、消费者及标识；准备期间发生上述变化则拒绝启用。所有调用仍须在所属硬件串行队列上进行，尚未接跨队列主机执行调度。

## 客户端串行主机执行调度

新增主线程 `HostTextDispatcher`：消费者显式提供文本计划、目标 PID 和会话凭据后才接受任务；逐个等待执行完成，避免多个文本的字符交错。最多保留 64 个待执行任务，超出时停止并报告，不静默丢弃。停止会取消正在执行的任务并清空待执行队列；重新提交的任务等旧执行器返回后再开始。执行失败停止同一队列并通知错误处理器。发送计数仍只是已发送 UTF-16 单元，不作为目标应用接受证明。

客户端 USB 观察回调改为传递 `HostTextTicket`，包含不可变 UUID 和受 NSLock 保护的有效性状态。停止、更换配置或断开会使旧凭据永久失效；主线程执行器不跨线程读取 USB 对象的可变属性。上节 UUID 标识仍保留在硬件队列上，新的跨队列消费者使用凭据状态。调度器为每次执行提供取消查询，结合会话有效性和自身队列代次；既有 Unicode 执行器在完整按下／释放事件对之间检查取消、目标焦点和修饰键。

新增 `--host-text-dispatch-self-test` 只使用替代执行器与本地任务调度，不调用 Unicode 执行器、不打开设备、不安装输入监听或查询权限。针对性检查通过：旧凭据拒绝、排队任务取消、停止后新任务不与未返回的旧任务重叠、有效任务按序执行、执行失败后剩余队列停止；原生编译和既有纯文本准备检查通过。该调度器尚未接产品服务／界面，真实焦点与 Unicode 输入仍待后续统一验收，网页跨应用主机能力和文本键位安装未完成。

## 客户端服务连接

新增 `HostTextService` 连接 USB 观察与主线程调度。构造服务不打开设备；显式 start 先停止旧服务，再验证型号 JSON 和辅助功能权限，不弹出权限申请。随后专用线程创建 USB 会话、读取默认／当前表并开启观察，持续运行其所属 RunLoop。USB 对象的读取、回调和释放均留在该线程，主线程只接收文本计划和加锁的会话凭据。事件交给主线程时选定前台目标 PID，执行器继续逐字符核对焦点；不会激活目标应用或给 CherryMac 自身输入。

停止先立即使旧凭据失效，再唤醒硬件线程结束观察并释放连接；旧准备完成通知、事件和错误通知通过服务代次检查拒绝。执行错误会停止整个服务并更新状态。服务析构也请求停止硬件线程。产品接线时须在开始配置写入、切换配置或关闭服务界面前调用 stop；其他 USB 会话或外部 Windows 软件的配置修改尚没有全局通知机制，不能把单一连接内部失效处理冒称已覆盖外部改动。
