# 文本与鼠标扩展动作的官方路径

本页基于用户提供的 CHERRY Utility 2.3.28.7 主程序与 CommFunc.dll 静态分析。没有执行 Windows 程序，没有向键盘发送测试包；这些证据不能替代本型号真机验收。

## 文本动作

主程序动作分派表 `0x4FF6F4` 将 ActionType 2 分派到宏事件路径，将 ActionType 3 分派到 `0x4FF341` 的文本路径。这是两个不同的动作类型。

文本分支读取 `ActionContent.ActionText`，调用字符串转换函数 `0x480FB0`，保存到设备对象的 `+0x2590` 文本表。该分支没有把文本转换为宏区的四字节事件；2026-10-03 核对 IAT `0x6EB87C` 后确认它是 DuiLib 的 `CDuiString::IsEmpty`：返回非零时跳过设置，返回零（非空）才写入 `A1 00 00`。此前“空字符串写入”的记录反了，现纠正。空文本保持零临时记录，由后续流程跳过更新，不能把它解释成禁用。

另一个文本调用路径在 `0x512EBA` 读取同一文本表，在 `0x512EF1` 传入操作值 `0x291`，通过对象的 `+0xA34` 函数指针调用。初始化路径 `0x4F68D3–0x4F68EB` 通过 GetProcAddress 取得 CommFunc.dll 的 `UniFunc2` 导出并保存该指针。

DLL 的 `UniFunc2` 在 `0x10001FF3–0x10002004` 识别 `0x291`，调用 `0x10001EC0` 创建线程。线程入口 `0x10001E30` 使用 GetForegroundWindow、GetWindowThreadProcessId、AttachThreadInput 与 GetFocus 获取主机上的焦点窗口，循环通过 SendMessageW 发送文本的 UTF-16 代码单元，消息数值为 `0x286`；循环跳过 `0x000A`。

这确认了官方存在依赖 Windows 主机的文本执行路径。仍需确认该型号的实体触发、ActionTextFlag 和非空文本键位编码，再决定完整移植方式。不能把任意 Unicode 文本当作已确认的键盘板载宏，也不能只凭这条路径排除其他型号或分支的实现。

完整移植目标保留文本功能。macOS 需实现对应主机端能力；浏览器页面的跨应用文本执行方式需要另行落实。当前两端仍原子拒绝未支持的文本绑定导入，避免静默丢失或生成错误硬件映射。

## Type 4／5 的纠正

早期宏协议文档将 Type 4／5 写为滚动，现已纠正。公共事件构造函数 `0x45C840` 对消息 `0x200` 的扩展路径，在 `0x45CB10` 选择事件字节 `0x84` 并读取 `kb_mouse_x_left_edit`，在 `0x45CBC5` 选择 `0x04` 并读取 `kb_mouse_x_right_edit`；后续分支对应 Y 轴控件。去掉事件字节最高位后，类型为 4／5。这是 X／Y 移动路径，不能当作滚轮方向或滚轮次数使用。

公共表还包含鼠标滚轮消息 `0x020A`，但已追踪的宏录制函数只匹配基本与扩展按钮消息，手工宏菜单只列出左、中、右、前进、后退五按钮。仅凭公共表不足以证明本型号能录制或执行滚轮，也不能排除尚未追踪的型号分支。暂不猜测滚轮编码，原始备份继续保留未知事件。

构造函数 `0x45C840` 的十个直接调用点位于 `0x45D8D0–0x45DAA2`，传入的是五个鼠标按钮的按下／松开消息；未见这些调用传入 `0x200`。软件资源的宏动作菜单也只有五个按钮及编辑／插入事件，尚不能据公共构造函数中存在轴移动分支就宣称型号 47 提供轴移动宏。继续追踪间接调用和型号 UI 分支；不据此删减完整功能目标。

## 文本触发的静态接收分派

继续追踪得到 `CEevisionKeyboardDevice` 表 `0x77F604` 的虚函数 `+0x32C` 指向文本执行函数 `0x512DE0`。不能仅搜索直接 `call 0x512DE0`；接收代码先加载函数指针再间接调用。通用接收路径 `0x50C227–0x50C266` 判断事件值在 `[0x0700, 0x0800)`，减去 `0x0700` 后把索引传给此虚函数。另一条接收路径 `0x50C69A–0x50C6C6` 做同样的区间与索引分派。后一条路径在 `0x50C4A8–0x50C4CA` 用接收缓冲区的字节 1 和 2 构造小端 16 位事件值；这只是该通用分支的布局，不能直接套到目标型号全部报告。

文本执行函数继续通过逻辑键值表 `+0x2130` 搜索索引，再从 `+0x2590` 文本表取非空内容，传给 `UniFunc2(0x291, ...)`。这进一步说明官方文本由专用事件触发后交给主机执行，不是普通键盘字母报告，也不是将整个文本写成宏事件。文本键位编码仍与触发事件值不同，不能把 `A1 00 00` 当作接收报告格式。

只读工具 `Tools/inspect-official-settings.py` 已增加虚函数目标核对及两个接收分支的八处指令核对；固定版本 SHA-256 后读取 PE 文件，不执行 EXE。原文件核对及四项 PE 工具检查通过。报告明确不证明型号 47 类选择、实际报告 ID／布局、文本实体执行或持久化。还需追踪 `046A:01CE` 的接口选择与报告描述符／接收入口，才能落实原生文本监听和网页端的主机能力范围；当前不生成真实文本绑定写包。

## 目标型号已保存的报告布局

新增纯文件工具 `Tools/hid-report-layout.py`，解析本地保存的 HID 描述符并统计各 Report ID 的输入／输出／Feature 长度，包含常量填充位和报告 ID；不会打开 HID、采集输入、发送请求或输出设备序列号。用目标型号已保存的 `keyboard-usb-capabilities.json` 核对得到：

| Report ID | 方向 | 含 ID 的总字节数 | 字段 Usage Page |
| --- | --- | ---: | --- |
| 1 | 输入 | 21 | 7（键盘） |
| 2 | 输入 | 7 | 1、9（鼠标） |
| 3 | 输入 | 3 | 12（媒体） |
| 4 | 输入／输出 | 64 | FF1C（厂商） |
| 5 | 输入／输出 | 9 | FF1C（厂商） |
| 6 | 输入 | 3 | 1（系统控制） |
| 8 | 输出 | 2 | 8（指示灯） |
| 9 | Feature | 30 | FF00（厂商） |

该表来自此前保存的目标 USB 描述符，不是本轮实时报告捕获。官方 `0x50B640` 创建接收线程 `0x50C3D0`，通用线程路径从其缓冲区字节 1／2 取事件值；另一个线程 `0x50B500` 指向 `0x50BEE0`，经过通用 HID 解析再分派。线程启动参数、接口／报告选择与型号分派尚须追踪。虽 Report 5 是短厂商报告，不能仅凭长度或字节位置就把它认定为文本触发报告；Report 3 同样可容纳 16 位值，Report 4 则已有不同用途。当前不把描述符存在视为实际文本触发或支持无线写入的证据。

工具检查覆盖多报告、填充位、Global Push／Pop、局部 Usage 重置、截断、无效 ID、未平衡集合与不支持的长条目拒绝，四项合成检查通过；本地目标描述符解析通过。

```sh
python3 Tools/hid-report-layout.py /绝对路径/已保存的能力资料.json
python3 Tools/test_hid_report_layout.py
```

实际宏测试仍使用独立研究 App；报告布局分析不改动其正在运行的会话，也不生成新的实体写包。
