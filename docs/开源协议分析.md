# CHERRY 开源协议分析

分析日期：2026-10-01。仅读源码和公开资料，离线分析数据，没有向键盘发送命令。

## 结论

灯效控制已有成熟程度较高的协议线索。改键协议也有贡献者的实测记录，但主项目没有把它做成完整功能；记录来自 MX 10.0，并不是无线宝可梦款。板载宏和断电后永久保存仍无足够证据。目前不能直接把任一项目当成官方 Mac 替代版。

## 核对的项目

- cherryrgb-rs：源码版本 `fed596e87e0e9deadccca67f70495cbe8b7f21a5`。主要查看 `cherryrgb/src/lib.rs`、`models.rs`、兼容表、CI 与研究文档。
- OpenRGB：CHERRY 控制器及检测代码，查询于分析日期。与 Rust 项目进行协议对比。
- felfert/cherryrgb-rs 的 reveng 分支：贡献者关于 MX 10.0 官方 USB 改键通信的研究记录。
- cherrymxboard30s-rgb：已归档的 Linux 灯效实现，提供补充来源。

## 数据包与 USB 传输

Rust 实现使用 HID 类请求 SET_REPORT：请求类型 `0x21`，请求 `0x09`，值 `0x0204`（Output、报告 ID 4）。请求发出后从 interrupt IN 端点接收回复。常见默认接口为 1、端点为 `0x82`；最新代码会对单接口设备改用接口 0 并寻找 IN 端点。这是通用适应代码，不能据此声称无线款已验证。

| 包偏移 | 含义 |
|---|---|
| 0 | 报告 ID `04` |
| 1–2 | 小端 16 位校验和 |
| 3 | 命令 |
| 4–7 | 命令参数；分块操作中为长度、两字节偏移、保留字节 |
| 8–63 | 分块数据，最多 56 字节 |

普通命令的校验和为偏移 3 至 63 字节的无符号和。Rust 对 `07`、`1B` 查询及回复只计算命令和四字节参数；这是该项目采用的特殊规则，尚未在无线款上确认。OpenRGB 的 C++ 实现使用 `char` 求和；Mac 移植应明确使用无符号字节，避免平台字符符号性影响结果。

## 已找到的命令

| 命令 | 源码/资料行为 | 可以确认到什么程度 |
|---|---|---|
| `01` / `02` | 开始 / 结束会话 | 不等于已确认 Flash 保存 |
| `03`，参数 `22` | 状态读取流程中的请求 | 确切字段仍未知 |
| `06` | 灯效参数 | Rust 和 OpenRGB 均实现 |
| `07` | 读取键位数据 | Rust 返回每项 3 字节 |
| `09` | 贡献者记录的整表改键 | MX 10.0 官方软件 A→B 实例；目标无线型号未验证 |
| `0B` | 写入逐键 RGB 数据 | 已有实现，但键位索引要按型号确认 |
| `1B` | Rust 解释为键索引读取 | OpenRGB 常量注释称其为颜色数据读取；解释存在差异 |
| `05` | 颜色重置流程发送参数 `01`、`19` | 含义未完全确认，不适合作通用初始化 |

### 灯效

Rust 灯效参数主包在偏移 4–8 放 `09 00 00 55 00`，随后依次为模式、亮度、速度、未知/方向字节、彩虹标志及 RGB。静态模式为 `03`、自定义颜色为 `08`；亮度为 0–4，速度为 0–4，数值越小越快。

Rust 会在主参数包后追加另一组参数，然后结束会话。不能只根据主包构造一条指令便假设整个流程等价。OpenRGB 使用相同命令，但逐键颜色块上限设为 54 字节，Rust 为 56 字节：54 可被三个颜色通道整除，56 会跨键拆块。需要按设备与固件核对，不能合并两个实现的常量随意使用。

### 改键：新增的关键线索

贡献者用官方软件在 MX 10.0 上把 A 改成 B，记录了三次信息请求、开始会话、七个 `09` 数据块、结束会话。七块的长度分别为六个 56 和一个 42，总共 378 字节，对应 126 个三字节记录。偏移是字节偏移，并不是物理键编号。

原研究中普通键记录形如 `20 00 04`（A），改为 `20 00 05`（B）；消费者控制键形如 `30 92 01`（计算器）。这支持“首字节可能区分键类型，其余两字节按类型解释”的推断。Rust 的 Keymap 字段命名为 modifier、unk、keycode，但不能把名称直接当成已验证的结构定义。组合键和宏的数据格式仍需继续确认。

126 是项目使用的表大小，不代表键盘有 126 个实体按键。原研究记录了占位项及重复项，且实体顺序与图上的从左到右顺序不同。不能用我们的键盘图索引直接覆盖板载表，必须先读取原表、定位实际键并保留未知条目。

### 离线验证发现的文档错误

解析贡献者前两组示例共 24 个 64 字节数据包：A→B 组全部校验通过；恢复组第一条 `09` 包未通过。恢复组只把目标字节从 `05` 改成 `04`，但保留旧校验和 `0544`，计算结果应为 `0543`。差异实际位于包的零基偏移 37，而文字描述写作 38。

因此这些文档片段适合用于研究，不适合直接作为可发送的恢复模板。已提供纯离线分析器 `Source/analyze_protocol.py`，检查包长度、命令及校验和，不含设备连接或发送功能。

## 无线抓包的进度

OpenRGB issue 4564 的申请者提供了无线 3.0S 的 USB 灯效抓包，设备为有线 `046A:00E3`、接收器 `046A:00EA`。这些 ID 不能与本机蓝牙 `0687:00E9` 直接等同。

本次尝试下载静态红、绿、蓝及亮度抓包，GitLab 返回 HTTP 403；尝试替代上传地址返回 404。已读到附件列表，没有取得 pcapng 文件，因此没有完成无线抓包内容的分析，也未据此生成写入命令。

## Mac 实现需要补足的环节

优先通过 IOHIDManager/IOHIDDevice 访问厂商报告，按描述符识别目标接口；不要直接照搬 libusb 的接口号或占用日常键盘接口。请求必须校验回复的报告 ID、命令、偏移、长度与校验和，并处理超时和不相关输入。Rust 当前 send_payload 会把解析失败转换成 None，校验失败仅写日志，部分会话错误路径也没有确保结束；移植时应修正。

真正接设备前仍需确认：USB VID/PID、报告描述符、键位表布局、组合键格式、宏存储结构、配置保存及恢复指令。接设备后需验证写入读取一致、断电保留、切回蓝牙有效。当前无需转接头即可继续做离线协议研究，但不能验证这些硬件结果。
