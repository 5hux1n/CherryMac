# 网页版 0.1.0 灯效写入异常

2026-10-02，用户反馈：通过网页版写入灯光配色后，键盘灯熄灭、无法使用，Mac 无法识别；Windows 仍可连接。用 Windows 配置恢复后部分键仍闪灯，再通过网页导入 JSON 并恢复后恢复正常。用户随后确认恢复用的是 Windows 官方 JSON，但不记得出问题那次选了哪种写入类别。

这是用户报告的实际故障。0.1.0 不能继续作为可用的硬件写入版本分发。

## 已采取的措施

- 0.1.0 GitHub Release 转为草稿，撤回公开下载；历史源码保留供排查。
- 0.1.1 移除执行设备写入的流程。页面按钮、配置入口及底层 USB 发送接口同时拒绝全部写命令和未知命令；没有启用写入的参数或开关。
- 仅保留设备信息、灯光参数、当前键位、颜色、宏区与 LED 索引的有界只读查询，以及本地编辑、导入导出、备份下载。
- 添加本地排查资料导出。包含浏览器版本、当前读取的配置、编辑区、历史备份及新版只读请求、回复、耗时和错误日志；不自动上传。另提供无设备访问的离线日志校验与快照差异工具。
- 所有测试与排查均离线或使用模拟设备，本次没有向实体键盘发送命令。

旧版已打开的网页不会自动变成只读版。请先关闭旧页面，再打开 0.1.1；不要再次运行旧包来复现故障。

## 已确认的实现差异

原生 `waitUntilKeysReleased()` 在每次调用中重新建立松键检测器，每个写入包前重新等待连续约 200 毫秒的松键状态。网页版 0.1.0 根据最近一次页面按键事件／鼠标确认时间等待，首次达到 200 毫秒后，后续包可以连续快速发送。等待上一个命令回复不等于复刻了原生逐包等待的发送节奏。

此前原生实物测试只同时修改两个键的 RGB；切换其他内置模式的测试大多只发一个参数包。它们不能证明网页版一次修改大量颜色的发送节奏可被硬件可靠处理。

网页版默认“全部待写入配置”还会包含此前编辑或导入的键位、宏及其他待写入数据。需要核对当时实际修改内容，不能仅凭正在编辑灯效就认定当时只发送了颜色命令。

0.1.0 遇到超时、无效回复或断线会关闭会话，无法继续回滚，因此可能留下部分修改。网页没有保存那次实际写入的包与时间记录，新的记录不能重建历史通信。

灯效写入包已用原生 `CherryPacket` 代码离线逐字节比对：126 个位置的 `0B` RGB 包与一个 `06` 参数包一致。这只排除了这些测试向量的编码差异，不能验证物理通信、固件执行、时序或实际故障时发出的内容。

**根因仍未确认。** 发送节奏是已确认的实现差异与调查方向，不能直接宣布它导致了本次故障，更不能只加延迟就重新开放写入。

使用 Windows JSON 与原生 0.7 转换结果离线对比，当前网页版转换生成的键位、灯效参数、逐键 RGB 和宏区均一致。用户后来确认了实际恢复文件，已在本地单独对比；文件与完整备份不放入公开仓库。这些结果不证明故障时配置正确。

## 可执行复现与代码修正

`Web/tests/reproduce-legacy.mjs` 从固定的 0.1.0 提交提取原始五个模块，记录源码哈希，在内存设备上执行原始配置写入与回复校验。不会打开设备接口。已用用户提供的七份备份与确认的 Windows 恢复文件运行，快照间变化作为候选操作，不能当成故障时的真实操作记录。

- 候选的逐键颜色加模式切换会生成 `0B` 后接 `06`，后者带入原模式的 `255` 颜色选项。在模拟即时回复条件下，两包间隔约 0.2 毫秒，证明旧版没有逐包等待；这个数值不是实体 USB 抓包结果。
- 注入“第一条颜色命令执行后回复丢失或校验损坏”，能稳定留下新颜色与旧灯效参数；会话被关闭，恢复入口拒绝继续发送。复现了失败处理路径，但没有证据证明历史故障发生了这种回复异常。
- 不注入错误时，内存设备能完成候选配置与恢复目标写入。它不模拟固件、灯光、供电或 macOS 设备识别，因此未复现实体熄灯／无法识别，也不能验证物理修复。

已修改参数校验：发送首九字节的新灯效参数时，方向和颜色选项必须是显式支持的值，不能因与旧配置相等就携带未知值。不会擅自把 `255` 改为 `0`。颜色单独变化且不重发参数的计划仍可验证。这里将 `255` 视为未知选项，不是认定它在原模式中无效。

已修改页面松键检查：每次重新观察至少 200 毫秒，期间即使按键快速按下并松开，也会中止。它仍只能观察页面输入，不能证明系统范围的松键状态。新增回归测试通过，全部硬件写入继续关闭。

独立复查官方安装包的灯效序列化函数，确认速度转换是 `4 - Speed`，颜色选项来自 JSON 布尔值；参数写入辅助函数使用 `06`，对应分支的标记为 `0x55`。现有导入速度与报文标记没有发现编码差异。静态分支分析无法确定实际运行分支、发送间隔与故障时回复，需要官方软件的实际 USB 抓包继续核对，不能直接照发未验证的其他命令。

## 2026-10-04：官方参数尾部与结束事务路径

新增只读工具 `Tools/inspect-lighting-sequence.py`，只读取固定 SHA-256 的官方主程序，不运行 EXE、不连接 HID、不生成或发送配置报文。它核对设备虚表中的 0x500790 灯效方法、45 处指令、`LightOpenFlag` 字符串以及 PE 导入表中的 `KERNEL32.dll!Sleep`。

在 0x5010D8 开始的备用分支，银行基址为调用参数左移六位，顺序为：

| 步骤 | 相对银行偏移 | 长度 | 数据来源 |
| --- | --- | --- | --- |
| 参数命令 06 | 0 | 9 | 已序列化灯效参数 |
| 参数命令 06 | 21 | 1 | `LightInfo.LightOpenFlag` |
| 参数命令 06 | 24 | 1 | 固定值 1 |
| 结束函数 0x4DA0E0 | — | — | 调用前先等待 10 毫秒；普通选择值发送 02，选择值 1 则发送 82 |

`LightOpenFlag` 来源通过 0x47ADE0 JSON getter 追踪：写入局部结构第 11 字节，复制给 0x500790 后落到参数第 21 字节。这里确认的是字段来源，不能据名称直接决定 0／1 的物理灯光含义。0x500BC0 的非零对象字段还控制是否先调用开始事务函数。

现有旧版网页及原生灯效路径只发送首九字节参数，没有复刻这条分支的两个尾部写入和结束调用。原生早期灯效日志中的参数第 21 字节为 0、第 24 字节为 1；数值原本相同不证明再次写入没有触发作用，也不能据此认定差异导致故障。结束函数的 10 毫秒等待不能当作每个颜色包之间的官方间隔。

这些证据仍有明确边界：未证明实际运行对象选择值、银行参数及调用者是否使用此分支；没有官方实机 USB 抓包；尚未追完颜色写入与这条参数分支的顺序；旧版故障本身没有通信日志。写入辅助函数会检查交换返回值和 FF／FE 回复，但这条高层分支在各辅助调用后直接继续下一步，不能据其最终返回成功就当作每个包均已成功。

工具在提供的主程序上核对通过；四项定向检查覆盖指令改变、错误延时导入、异常导入范围、未知 EXE 拒绝。本次没有修改产品 HID 授权或开放灯效写入，没有把命令 02、尾部参数或延时直接加入产品发送。根因仍未确认。下一步继续追踪实际型号分支条件、尾部字段与颜色事务调用关系；实际写入须留到宏统一验收之后。


### 型号选择条件的只读核对

工具增加 38 个比较条件，逐一核对对象字段 `word [object+0x1e1a]` 的读取、比较和条件跳转字节，解析六组等值目的地址。若该字段为 `0x01CE`，它不属于任何专用分支，落到 `0x5010D8` 的首九字节、偏移 21、偏移 24 和结束调用路径；`0x00CE` 则属于直接返回组，不能混淆两个值。这里仍是条件分析，尚未证明该字段由本型号 USB PID 赋值，也不是实际设备执行记录。

固定官方 EXE 的核对通过；工具六项定向检查通过，覆盖六组目的地址、CE／01CE 区分、非法输入以及读取／跳转指令改变拒绝。无 HID、权限或输入服务操作。产品灯效写入保持关闭。


## 官方颜色方法与上层调用顺序

同一固定 EXE 的虚表 `+0x2C4` 指向 `0x501190`，颜色辅助函数为 `0x4DCDE0`。只读核对工具增加 69 处指令校验，分开记录主 RGB 表路径与尚未分析完的备用路径，避免混用。

主 RGB 表路径受对象 `+0x2240 != 0` 控制，按映射容器查找槽位，在缓冲区 `mappedIndex*3+channel` 写三通道。计算为 `(component * fourthColorByte) >> 8`；尚未把内存中的第四颜色字节连回 JSON `Alpha`，因此不能直接据此修改现有文件导入／导出，也不能将 `/256` 改成常见的 `/255`。

颜色命令 helper 对普通传输选择值使用 `0B`，选择值 1 使用 `8B`；report ID 为 4，第 7 字节为 0，偏移为第 5／6 字节小端，数据从第 8 字节开始，块容量来自对象 `+0x690`。校验和累加第 3 至 63 字节。辅助函数在交换失败或 FF／FE 状态后返回，停止后续颜色分块。

对象型号字段不属于 `01DA/01E6/01EF/014C` 时，颜色银行基址是调用参数左移九位，发送总长是映射容器大小乘三；这不等于已验证本型号银行参数与表长度。颜色方法也有条件开始和结束事务调用；颜色 helper 返回失败时仍调用结束函数，随后等待 200 毫秒，最终返回 0，没有检查结束函数返回值。不能复制这个高层返回值策略作为产品成功判据。

在上层 `0x4B1930` 找到一条明确调用链：先调用参数虚方法 `+0x2BC`，随后读取灯效状态，第一字节等于 21 时调用颜色虚方法 `+0x2C4`。getter `0x4EC730` 将对象 `+0x215C` 的 47 字节状态复制给调用者。这是一处静态调用顺序，不是所有按钮流程的通用顺序或实际 USB 日志。旧版网页候选过程是先颜色、后参数，两者在此调用点存在差异；仍不能据此确认历史故障原因。

固定 EXE 核对通过，八项定向工具检查通过（新增银行移位、校验和、调用虚表及颜色方法身份被改时拒绝）。没有修改产品发送流程、打开设备或重新触发故障。下一步追踪本型号颜色映射初始化、第四颜色字节来源与配置页实际入口。


## 颜色第四字节与官方亮度加载

已追到 JSON getter 0x483680 的现有颜色记录路径：CustomLightMode.LightColorInfo[group][index] 的 Red／Green／Blue／Alpha 分别写入四字节结构。getter 返回的颜色列表经 0x4F4CF0 赋给对象 +0x2150。两个加载方法 0x505900 和 0x5059F0 随后循环全部条目，把第 3 字节覆盖为亮度查表值；索引取对象 +0x215D，表地址 0x74A350。前五档为 0、65、135、195、255。

因此在这两条路径中，JSON Alpha 不是最终发送的颜色强度；逐键颜色方法使用的是加载后覆盖的第四字节。缩放仍为乘积右移八位，例如通道 255 乘系数 255 得到 254。尚未证明当前型号配置页实际进入这些加载方法、亮度字段赋值来源和其他编辑路径是否覆盖 Alpha，不能推广成所有调用的统一规则。

工具增加 38 处指令、JSON 字符串和五档表校验，实际固定 EXE 核对通过，工具十项检查通过。产品模型另外补齐所有逻辑颜色（包括未映射位置）的 RGB 校验，以及提供 Alpha 时的 0～255 整数校验；有效 Alpha 和未知字段保留，不添加未提供的 Alpha，不修改颜色缩放／HID 流程。Web 两项定向检查、原生编译及纯灯效文件检查通过。新源码尚未纳入既有 App 0.19.0／PHP 0.13.0 包。


## 默认按键槽位与 LED 颜色槽位的区别

追到初始化 0x4FC140：07／87 helper 0x4DC2D0 提供默认键位数据到对象 +0x2730；1B／9B helper 0x4DC850 提供独立 LED 索引到 +0x2B30。后者长度由 helper 首 WORD 除三决定。初始化随后调用 0x5031F0 构建两个向量。

01CE 所在的非零且非 01BA 条件分支，用 0x76C6C8 的 126 条参考记录匹配默认表，选择首个相同三字节记录：键位向量保存物理按键槽位，颜色向量保存 LED 索引表在该槽位的值。未匹配位置为 FF；逻辑颜色 122／123／124 最后强制 FF。只有另一个 00B4 分支直接使用按键槽位作为颜色槽位。不能把这个例外套到本型号。

两端增加纯函数 resolveLightingSlots，接收默认表和 LED 索引数据，不进行读取、监听或写入。按固件逻辑参考匹配首个记录，保留缺失／FF／禁用项为空，允许共享 LED；当前颜色银行只有 126 个 RGB，所以非 FF 的索引超出 0～125 时拒绝，不截断。检查覆盖非一致／逆序表、单独 LED 位移、首个重复优先、缺失索引、禁用项及长度／越界拒绝。原生编译和纯文件检查通过，Web 定向检查通过。

静态工具新增 38 处映射读取与解析指令核对，固定 EXE 核对及十一项工具检查通过。现有配置导入／导出 UI 仍使用既有固定槽位转换；新解析器还未替换此路径。以前只读研究确认 109 个可见位置 LED 索引非 FF，未保存全部索引值，不能据此证明 LED 表为恒等映射。旧版两键颜色读回成功也不能证明实体按键与灯珠对应正确。下一步需把带设备来源的默认表／LED 表纳入配置模型，再替换颜色草稿转换和预览；用户暂停期间不发起设备查询。


## LED 元数据进入两端产品模型

可选 lightingMapping 已接入普通配置文件及官方颜色导入／导出，包含两张映射表及对应 deviceInfo。两端先检查固件信息与配置一致，再解析独立 LED 槽位；此检查不等于实时设备来源认证。键盘图预览、取色、配色、熄灭和颜色变化标记也使用此数据，无灯位置拒绝配色。键位与宏索引保持使用原按键槽位。

暂未自动向设备查询或附加该字段，旧文件继续使用固定槽位草稿转换。当前只完成带元数据文件的转换与界面接线，不是取得本型号真实 LED 表或证实灯珠一致。四项 Web 定向检查、两种原生编译、原生纯模型检查，以及临时文件 Web→Mac→Web 完整快照／映射往返通过。原生与网页包未更新，硬件发送路径未修改。


## 官方自定义颜色的离线准备与逆转换边界

两端增加 officialCustomColors 和 prepareOfficialCustomColors，按已追踪加载路径的五档系数 0/65/135/195/255 计算 `(raw * coefficient) >> 8`。后者仅接受本型号完整官方模板、自定义 SelectItem=21、当前完整颜色表与有效 LED 映射；JSON RGB 作为原始颜色，Alpha 校验后不参与这条全局亮度覆盖路径。按已追踪官方方法先清零输出表，再填入解析到的 LED；未映射位置保持零，输入不修改。

新增 officialRawChannelRange 返回一个存储通道可能对应的原始通道范围；不可能生成的数值明确拒绝。例如最大档 raw=255 生成 254，存储值 255 不能由该规则生成；零档的存储 0 可对应任意 0～255，无法唯一恢复。不能对读回颜色再盲目缩放，也不能声称从存储银行直接构建的 Windows JSON 等同于原官方编辑颜色。当前 Windows 导出仍明确为草稿。

这些函数是离线算法组件，未接入真实发送或改变现有默认导入／导出语义，也未据此开放灯效。Web 两项定向检查覆盖五档整数结果、所有通道的逆范围、非恒等映射、未映射 LED 清零、输入不变及不支持模式拒绝；原生纯灯效模型检查覆盖同类边界。实际型号运行是否使用这条加载路径、实际灯珠外观、事务银行和故障根因仍未证明。


## 分支字段的设备身份来源已静态追踪

新增 `deviceIdentityAudit`，在同一已锁定 SHA-256 的 EXE 中核对 33 个指令位置和 HID API 导入，补齐原先“字段是否为 USB PID”的证据链：

- `0x5447de` 调用 `HID.DLL!HidD_GetAttributes`，结构位于连接对象 `+0x26c`。依照 [Microsoft HIDD_ATTRIBUTES 定义](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/ns-hidsdi-_hidd_attributes)，ProductID 位于该结构 `+6`。
- 枚举使用连接对象 `0x8433b0`；`0x496c67/0x496c6d` 将 `0x843622` 的 ProductID 写入本地设备记录 `+2`。`0x4977e0` 逐项核对注册表及既有设备列表的同一字段，没有把它当成模式编号。
- `0x498b52..0x498b83` 从设备列表取得一条 `0xa0` 字节记录，经 `0x498270` 复制构造，再传入 `0x5435a0`；后者将记录赋值到键盘对象 `+0x1e18`。赋值函数 `0x429100` 把源记录 `+2` 复制到目标 `+2`，因此分支字段 `object+0x1e1a` 在这条打开路径上就是 ProductID。

由这条静态链可以推导，本型号 ProductID `0x01CE` 进入 `0x5010d8` 分支；首九字节、偏移 21、偏移 24 及结束调用不再只依赖未经追踪的字段假设。`0x00CE` 仍属于另一直接返回分支。此前相应段落保留为分析历史，这一节更新其证据状态。

真实会话执行、其他赋值路径、传输选择字段、配置编号、灯效参数语义和故障根因仍未确认。旧灯效实现未覆盖这些尾部与结束步骤，存在明确差异，但不能据此断言这就是此前熄灯故障的唯一原因。灯效硬件写入保持关闭。工具通过真实 EXE 校验，12 项工具检查通过，包含修改复制偏移或 API 导入后必须拒绝；没有启动 EXE 或访问 HID。


## 传输分支、配置编号与颜色缓冲区的进一步核对

审计工具新增 29 处字节核对，将 `record+0x9c -> object+0x1eb4 -> 0x4de640 第五参数 -> transport+0x44` 连起来。这与记录 +8 的连接分派字段不同。三个已核对本型号注册记录的末尾字初始化为 0；该值对应参数命令 06／标志 55、颜色命令 0B 和结束命令 02。值 1 则对应参数标志 0、颜色命令 8B 和结束命令 82。实际枚举列表如何填充该尾字段、是否还有后续更改仍未完成追踪，不能从注册值直接断言实时通信值。

静态灯效调用者 `0x4b1930` 两次读取键盘对象 +0x1ec0 指向的同一控件，经 `0x42b4b0` 取控件 +0xb24 的值作为参数与颜色的配置编号；不是直接固定为 0。控件身份、初始化、有效范围及实时选择仍待核对。

已新增五处颜色缓冲区初始化核对：`0x5011ab..0x5011c5` 清零 512 字节，随后只向成功映射位置填入缩放 RGB。两端官方颜色离线准备函数据此改为未映射 LED 输出零，纠正先前保留旧数据的差异。普通草稿配色和草稿导出不因这条分析自动改语义；函数仍没有接入任何发送入口。本轮检查限于源码／原始 EXE 文件与纯模型，没有 HID 或权限操作。


## 配置编号同时决定地址与参数首字节

已核对 `DeviceProfileItem` 查找／默认初始化／选择 setter。其 getter 返回的编号不仅在参数方法中计算 `bank << 6`，还经 `0x5007fd/0x500800` 写入首九字节的第一个字节。颜色方法独立计算 `bank << 9`。这三处必须使用同一明确的选择值；现有 bank 0 完整快照不等于其他编号的基线。

两端纯文件参数准备函数输出 `[bank, mode, brightness, 4-speed, direction, multicolor, red, green, blue]` 和经过字节范围校验的 LightOpenFlag。缺少字段、错误模式索引、亮度／速度越界或不可表示的 bank 拒绝。它不保留备份中的首字节，也不生成发送权限；实际配置数量、当前选择和 LightOpenFlag 物理含义仍待确认。保留原有草稿导入／导出行为。
